## 2. 账号文件约定

| 文件 | 用途 | 是否随仓库提交 |
| --- | --- | --- |
| 根目录 `account.example.json` | 空白填写模板，帮助新环境了解格式 | 是 |
| 根目录 `account.json` | 本机实际默认账号 | 否，加入 `.gitignore` |

两个文件采用相同结构：

```json
{
  "username": "",
  "password": ""
}
```

- 路径以 `free_rollcall_cli.py` 所在目录为基准，不受启动命令所在目录影响。
- 首次运行缺少 `account.json` 时，在固定位置创建空白文件，显示完整路径，然后直接进入手动输入。
- 创建文件时不覆盖已存在的文件；无写入权限时给出提示，交互终端仍可手动登录。
- 文件为空、格式错误、字段缺失、类型错误或字段为空时，说明问题并进入手动输入，不改写原文件。
- 账号去除首尾空白；密码保留原始字符，不做自动裁剪。
- 密码可以在用户输入时显示，但程序不额外回显已保存密码，不把密码、完整配置内容或认证凭证写入日志。
- 手动输入不使用账号格式正则，不限制长度、字符种类或账号形式；账号仅去除首尾空白，密码保留原样，交给网站判断。空输入只提示重新填写，不计认证失败次数。
- 新环境从远程拉取代码后可以启动；首次默认账号登录需要填写本机 `account.json`。
- 正常更新代码不会改写本地账号文件；README 同时说明模板、实际文件位置与填写方法。

## 3. 启动与终端交互

### 已有有效账号配置

1. 显示现有标题。
2. 显示 `2 秒后使用默认账号登录，按 Enter 手动输入`。
3. 在 2 秒内按 Enter：显示账号、密码输入提示，读取本次凭证。
4. 超时：使用文件中的凭证。
5. 调用业务层登录，成功后进入现有课程列表和查询流程。

### 缺少有效账号配置

显示文件位置或配置问题，跳过倒计时，直接进入手动输入。

### 输入机制

- 使用标准库实现超时按键等待，不新增依赖。
- macOS / Linux 与 Windows 分别采用适合各自终端的实现，只在对应系统加载相关模块。
- Enter 是唯一的切换键；其他按键不切换模式，倒计时阶段的残留输入不能进入后续账号或课程输入。
- 不启动一直等待输入的后台线程，避免它抢走后续课程编号。
- 退出、异常以及 Ctrl+C 均应恢复可能调整过的终端状态。
- 输入不是交互终端时，跳过倒计时，使用有效的默认配置；无法取得凭证时明确报错退出，不等待不可见的输入。
- 不支持限时按键的运行面板，提示用户选择登录方式，采用普通输入回退，避免启动直接崩溃；README 推荐使用真实终端。
- 本次只完善登录入口，后续课程选择仍保持交互；完整无交互运行参数、批量查询和结构化输出另行迭代。

## 4. 业务层登录改造

### 职责与调用方式

命令行负责账号文件读取、倒计时、人工输入和提示；业务层只接收凭证并执行认证，不读取账号文件或终端输入。

现有登录入口已改为：

```python
async def login_and_get_cookie(
    username,
    password,
    log=_ignore_log,
    *,
    allow_browser_fallback=True,
):
    ...
```

- 保留异步调用方式与成功返回值 `(cookie, student_id)`。
- 默认日志回调仍静默，命令行继续使用 `terminal_log.py`。
- 删除为桌面端服务的 `browser_channels` 参数及 Edge / Chrome 逐个回退分支，统一使用现有 Playwright Chromium。
- `allow_browser_fallback` 用于控制额外认证时是否允许打开可见浏览器；命令行正常交互时允许，非交互输入时关闭。后续脚本可显式关闭。
- 凭证错误抛出 `InvalidCredentialsError`，由命令行重新收集输入并累计次数；需要人工认证且关闭回退时抛出 `BrowserLoginRequired`；浏览器或网络故障抛出 `LoginError` 并结束本次运行。前两者均继承 `LoginError`。
- 新增 `login_in_browser(log=...)` 作为人工网页登录入口，供命令行在三次凭证错误后调用；成功返回值仍为 `(cookie, student_id)`。

### 登录流程

1. 在实施阶段先只读核实实际统一身份认证页面的账号框、密码框、提交按钮、登录模式与错误提示，再确定定位方式，不凭字段名称猜测实现。
2. 继续通过原网站和原浏览器认证流程，默认后台运行，自动选择适用的账号密码登录模式、填写并提交。
3. 判断认证结果，区分成功、凭证错误、验证码或额外认证、网络失败和超时。
4. 成功后沿用原有请求监听、学生标识提取、必要时访问课程签到页、登录凭证提取流程。
5. 无论成功、失败或取消，都关闭本轮浏览器及相关资源。

### 额外认证与失败处理

- 明确的账号或密码错误：允许在终端重新输入，连续认证失败 3 次后打开网页登录页。默认文件账号的一次认证失败也计入；不自动反复提交同一凭证，网络错误不计为密码错误。
- 验证码、账号锁定或其他需要人工参与的认证：允许回退时提示并打开可见浏览器，交由用户完成；可能早于第三次凭证错误。关闭回退时明确报告需要人工认证。
- 回退时关闭后台浏览器，打开新的可见浏览器，提示用户在网页中重新登录；不迁移后台认证状态，也不重复提交已失败凭证。
- 若实际网站始终要求人工验证，应如实记录这一限制；本次不增加验证码绕过、直接模拟认证加密协议等额外机制。
- 异常信息不包含账号文件内容、密码或完整登录凭证。

- 用户反馈多次登录失败或超时后，使用本机配置复现；未改写账号文件，诊断输出隐藏账号、密码、登录凭证与学生标识。

- 确认超时发生在等待账号表单显示时：实际登录页会继续跳转并由脚本显示扫码入口，原代码只即时检查一次账号登录链接的可见性，检查过早就跳过切换，随后等待一直隐藏的表单。
- 复现时尚未提交账号密码；页面的装饰图片另有请求失败，但核心页面已正常加载，不能把该图片请求失败当作本次认证失败的原因。
- 修复为等待“账号输入框”或“切换账号登录的链接”出现，再判断是否切换，随后等待两个实际输入框可见。
