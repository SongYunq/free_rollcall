## 1. 结论

这个仓库确实包含雷达签到实现。它不读取设备的真实位置，而是根据服务端返回的距离推算候选坐标，再提交经纬度。就这一实现本身而言，不需要设备定位权限，但仍然依赖服务端接受坐标数据及特定的距离反馈行为。

此前“没有雷达实现”的结论只适用于本项目根目录的 Python 源码及其 Git 历史；新拉取的第三方仓库提供了额外的实现参考。官方企业微信流程需要定位权限，与此仓库不调用设备定位，并不矛盾：二者的坐标来源不同。

数字签到部分与本项目重合：从同一详情接口读取数字码。参考仓库还包含提交步骤，补充了本项目原先没有的能力线索。

## 3. 雷达实现的实际原理

`send_radar` 的处理顺序：

1. 使用代码中两个预设坐标构造请求，调用同一个雷达签到提交地址。
2. 如果其中一次响应状态为 200，函数直接返回成功。
3. 否则读取两次响应中的 `distance` 字段。
4. 把经纬度近似转换到平面，以两个预设点为圆心、反馈距离为半径，求两个圆的交点，得到最多两个候选位置。
5. 将候选位置转换回经纬度，依次尝试提交，仍以响应状态 200 判断成功。

请求包含经纬度、精度、高度和设备标识等字段。坐标与精度由程序构造，没有调用操作系统位置服务。监控入口曾读取账号配置经纬度的语句已经注释掉，不是当前执行路径。

重要边界：前面的两次所谓探测也是实际的 `PUT` 提交请求，不是只读距离查询，有可能已经完成签到。因此，本次未通过运行它来验证距离反馈；后续任何在线验证都必须作为一次实际签到流程处理，不能在后台当作无副作用的接口探索。

### 对手机端位置权限的含义

- **本版确定采用计算坐标路径**：不读取设备位置，不申请位置权限，也不增加真实定位备用分支。
- 请求仍向学校发送位置字段；“无需系统定位权限”不等于“服务端不需要坐标”。
- 当前确认了源码实现，未实测服务端距离和提交行为；按用户要求，不以这些线上验证作为移植前置条件。

## 5. 已知特点与移植边界

- **成功判断**：数字和雷达函数都主要以 HTTP 200 判断成功，缺少本人签到状态复核。按用户决定，雷达保留这一判据，不增加额外成功门槛；数字签到仍按主计划核对业务结果。
- **异常处理不完整**：雷达函数没有设置请求超时，也未处理非 JSON 响应、缺失或无效的距离；甚至在检查首个响应状态前就解析正文。
- **计算有前提**：假设两次距离针对同一位置、距离与平面近似兼容；没有充分处理相切误差、负开方等数值边界。
- **设备标识策略**：每次构造请求都生成新标识，本次雷达移植保持一致；不擅自改为固定设备标识。
- **不照搬自动监控**：参考项目持续轮询并自动处理多个活动；我们的第一版仍由用户点击具体条目发起，绑定当前账号、课程与日志。
- **不以接口名判断类型**：`radar/rollcalls` 被用于数字和雷达；没有数字码也不代表一定是雷达。
- **原有登录继续独立验证**：仓库说明提到登录组件变更和兼容问题，不因此替换本项目已经验证的原页面登录原理。

这些问题来自静态审阅，不是本轮复现出的线上故障。参考仓库保持原样，未做修补或运行测试。

移植保持正常响应路径、请求字段、初始坐标、数学常量、计算公式、尝试顺序和提前返回逻辑一致。应用可以在外围把网络或解析异常转成错误提示，并防止重复点击；不改变参考算法、不新增候选位置、不增加自动重放，也不以线上验证作为交付条件。
